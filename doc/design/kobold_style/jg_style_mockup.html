Gremlin UI Redesign Overview

Design background

Everything follows from a handful of rules. If something in the prototype seems to break one, that's worth flagging.

  • Everything visible at once. No progressive disclosure — no accordions, drawers, "advanced" sections, or anything that hides state behind a click. Hover may add a tooltip, but never changes the layout.
  • Colour carries state, never decoration. The accent (blue here) means only: selected, focused, active. It's never a filled button or a coloured header. It's also user-changeable, so it deliberately does no heavy lifting.
  • Structure comes from lines and indentation, not boxes. Nested actions are shown with a thin guide line and a 16px indent — no tinted bands, no cards inside cards.
  • Desktop application. Gremlin is used on desktops, so no mobile-inspired behaviour, touch-supporting interfaces, or sizing.
  • Colour theme support. The theme will support defining colour themes through a text/QML file to modify the colours used, based on fixed colour tokens.
  • Scale support. The UI will support rendering at 100%, 150%, and 200% zoom levels.

Intent behind choices

  • The left list is deliberately not denser than before. The old app's space problem was never the input list — it was the right pane.
  • Action names are borderless text. This reduces visual clutter while still permitting modifying the text.
  • Guide lines only appear where actions branch. A leaf action indents but draws no line, so the lines in the pane are a map of exactly where nesting happens.
  • "Add action" is a quiet menu button, not a bright button, because it repeats many times down the tree and a row of bright buttons would be noise.
  • The left-pane "chips" summarise an input's actions as plain text with a "+n" overflow. They're derived live from the actual tree.

Interactive elements

  • Adding actions via drop down.
  • Updating of action chips.
  • Updating of action descriptions.
  • Switching between physical devices.
  • Folding of actions.

Other bits may appear interactive but don't mock functionality. Also, action logic isn't correct and is just hallucinated behaviour.

Feedback

  • Does the nesting read clearly — can you tell config apart from nested actions, and see which slot an action sits in?
  • Is the interface readable enough, i.e. the balance between compactness and space?
  • General feedback on the UI — what works, what doesn't?
